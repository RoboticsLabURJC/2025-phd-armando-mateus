Driving Metrics Framework, Best Model to Date, and First Steps with Behavior Metrics

September 29, 2026

📊 Part 1 — Evaluation Metrics Before Behavior Metrics

Before integrating an external evaluation framework (Behavior Metrics), we consolidated a set of driving quality metrics that we had been developing in-house. These metrics are computed by the LaneMonitor class, which updates every frame in both the PyTorch and TensorFlow drivers. All metrics are identical across frameworks, ensuring fair comparison. This section summarizes the exact definitions and formulas behind each one.

📌 Why This Matters

Closed-loop driving quality cannot be reduced to a single number. A model can stay on the road but oscillate constantly, or take curves well but at dangerous speeds. The LaneMonitor breaks down driving quality into orthogonal dimensions: lane keeping, smoothness, efficiency, curve handling, speed adaptation, and lateral zigzag.

🛣️ Correct Driving / Inside-Lane State

Every frame, LaneMonitor.update() queries CARLA for the nearest waypoint to the driving lane and evaluates three conditions in order:

  1. Is there a Driving-type waypoint? If not, the frame is marked "outside" (no driving waypoint or wrong lane type).
  2. Distance to lane center: distance_to_center = distance(vehicle, waypoint_center). If it exceeds lane_width * 0.7, the frame is marked outside ("Outside center").
  3. Angle with respect to the lane: angle_diff = normalize(vehicle_yaw - lane_yaw). If |angle_diff| > 80°, the vehicle is considered crossing or going against traffic, and also counts as outside.

Only if all three conditions pass is the frame marked is_inside = True with reason "Correct driving". Every transition from inside to outside counts as a lane invasion event (lane_invasion_count).

📉 Percentage Outside Lane
outside_percentage = (outside_time / total_driving_time) * 100

outside_time accumulates, frame by frame, the real elapsed time (dt) of all frames where is_inside = False. It is not a frame count: it is accumulated real time, so a brief exit at high speed does not weigh the same as a long exit at low speed.

🎯 Driving Smoothness
smoothness_score = (smooth_steering_events / steering_changes) * 100

Each frame computes steering_change = |steering_current - steering_previous|. If that change is less than 0.05, it counts as "smooth" (smooth_steering_events); if it exceeds 0.3, it counts as "aggressive" (aggressive_steering_events, tracked but not directly printed). Smoothness is the percentage of frames where the steering wheel did not make sudden jumps between consecutive frames.

⚡ Efficiency (Proposed Metric)
efficiency_ratio = throttle_accumulated / max(1, brake_accumulated + 0.001)

This is a proposed metric that is not yet fully validated for this project. throttle_accumulated and brake_accumulated are the frame-by-frame sums of the throttle and brake values applied (0.0–1.0 each) over the entire run. It is a ratio, not a percentage: the higher, the less the vehicle braked relative to how much it accelerated.

Note: In the current model, a constant speed of 15 km/h is maintained throughout the run, so this metric is not yet discriminative between models. It remains a proposal for future evaluations where speed control becomes a variable of interest.
🔄 Curve-Taking Quality

A curve episode is defined as a contiguous stretch of frames with |steering| > curve_enter_threshold (0.15). To avoid fragmenting a curve due to noise, the episode does not end until |steering| drops below curve_exit_threshold (0.05) — hysteresis.

During each episode, the following are tracked:

  • max_cross_track_error: maximum distance to lane center reached in that stretch.
  • had_lane_exit: whether at any frame of the curve is_inside = False.
  • oscillations: every sign inversion of steering within the same curve (while |steering| > 0.05) — a sign of overcorrection.

The final report computes:

turn_success_rate = (1 - curve_episodes_with_lane_exit / curve_episodes_count) * 100 avg_cte_in_turns = curve_max_cte_sum / curve_episodes_count avg_oscillations_per_turn = curve_oscillations_total / curve_episodes_count
  • turn_success_rate: % of curves taken without leaving the lane at any moment.
  • avg_cte_in_turns: how far from center the vehicle gets, on average, in curves.
  • avg_oscillations_per_turn: how many times, on average, the model overcorrects (zigzag) within the same curve.
🏎️ Speed in Sharp Curves vs. Straight
avg_speed_sharp_turns = sharp_turn_speed_sum / sharp_turn_speed_samples # |steering| > 0.6 avg_speed_straight = straight_speed_sum / straight_speed_samples # |steering| < 0.05 speed_reduction_in_turns_pct = (1 - avg_speed_sharp_turns / avg_speed_straight) * 100

Each frame of update_speed_metrics is classified according to the current steering: if it is a sharp curve (same threshold as "sharp turn", 0.6) it adds to the curve speed accumulator; if it is a straight stretch (|steering| < 0.05) it adds to the straight one. The reduction compares both averages: it measures whether the model actually brakes when turning hard, or maintains the same speed regardless of the curve — which would be a problem even if it takes the curve geometrically well.

〰️ Lateral Zigzag (Steering Oscillation)

Unlike "per-curve" oscillations, this measures zigzag over the entire run, including straight stretches:

  • Zero crossings: every sign inversion of steering (ignoring |steering| < 0.05 as normal noise/jitter). The total and the rate are reported: steering_zero_crossings_per_sec = global_zero_crossings / total_driving_time.
  • Steering standard deviation (steering_std): np.std() of the entire steering history of the run — how much the steering wheel varies in general, regardless of sign.
  • Dominant oscillation frequency (FFT): the mean is subtracted from the steering history (to discard constant bias) and np.fft.rfft is applied. The frequency-0 component (DC) is ignored and the one with the largest magnitude is taken:
avg_dt = total_driving_time / (total_frames - 1) spectrum = |FFT(steering - mean(steering))| dominant_frequency = frequency with largest magnitude (excluding 0 Hz) dominant_period = 1 / dominant_frequency

This distinguishes a periodic zigzag (a symptom of something systematic, such as an exponential smoother bouncing or an overcorrection repeating every N seconds) from simple random model noise. A high and consistent dominant_oscillation_hz across runs is more concerning than a high steering_std alone, because it indicates a pattern, not just variability.

⚠️ Observed Limitations

The metrics reveal two clear limitations of this model:

  • Oscillations on straight stretches: The model shows 510 steering zero crossings (0.57/s), a steering standard deviation of 0.083, and a dominant oscillation frequency of 0.02 Hz (period ~47 s). This indicates a low-frequency zigzag pattern on straight roads — not random noise, but a systematic periodic correction.
  • Lane exits during curves: Of the 84 curves taken, 15 (17.9%) involved a lane exit. The average maximum cross-track error in curves is 0.8 m, meaning the vehicle deviates noticeably from the lane center during turns. The curve success rate is 82.1%.

✅ Despite the Limitations: Continuous, Collision-Free Driving

Despite these issues, the model never leaves the road. Even when it exits the lane during a curve, it recovers correctly, achieving continuous driving without collisions. The demonstration video shows a 15-minute uninterrupted drive with 3.7 km traveled and zero collisions — the best result obtained to date.

🔄 New Models Currently in Training

Based on the successful configuration from Week 40 (composition 1, seed 456), new models are currently being trained in search of variants that maintain the collision-free performance of the current best model while improving two specific weaknesses:

  • Reduce lane exits during curves — currently 17.9% of curves involve a lane departure.
  • Decrease straight-line oscillations — currently 0.57 steering zero crossings per second with a dominant 47-second periodic pattern.

The goal is to find a configuration that preserves the 15-minute continuous, collision-free driving capability while delivering smoother, more stable lane-keeping behavior.

🚀 Part 3 — Starting Work with Behavior Metrics

🔄 Current Phase: Initial Setup

We have begun the process of integrating Behavior Metrics as an external evaluation framework for our driving models. Work is currently focused on operating system configuration for installation and operation.

✅ Work Completed So Far

  • OS-level configuration: Preparation of the environment for installing Behavior Metrics dependencies.
  • ROS bridge installation: Initial setup of the ROS bridge to enable communication between Behavior Metrics and the CARLA simulator.

📌 Current Bottleneck

No major progress has been made yet due to version compatibility issues across all the packages that need to be installed. The ROS bridge, Behavior Metrics, and CARLA all have specific version requirements that must be aligned. This is the main obstacle at the moment.

📌 Next Steps for Behavior Metrics
