CUDA Training Randomness and Behavior Metrics: First Successful Run with CARLA in Docker

October 6, 2026

🎲 Part 1 — CUDA Training Randomness: Why the Same Seed Produces Different Models

📌 The Problem in One Sentence

The training script fixes the PyTorch seed, but the GPU computes convolutions with algorithms that do not guarantee bit-for-bit identical results. That minimal difference grows with every training step until it produces completely different models.

🔍 How the Problem Was Found

While running entrenar_definitivo.py with the same dataset and the same --seed 42, we noticed that each run produced a model with different best_val_loss and different driving behavior. At first this seemed impossible: the seed was fixed, so the weights initialization, dropout, and batch order should all be identical. To investigate, we ran the same command twice with a small number of epochs and compared the per-epoch train_mse and val_mse lines:

python entrenar_definitivo.py --csv datasets/<dataset>/data.csv --epochs 3 --seed 42 > a.txt
python entrenar_definitivo.py --csv datasets/<dataset>/data.csv --epochs 3 --seed 42 > b.txt
diff <(cut -d'(' -f1 a.txt) <(cut -d'(' -f1 b.txt) && echo "IDÉNTICAS"

The cut removes the per-epoch time (which always varies). The result was not "IDÉNTICAS": the losses diverged starting from the very first epochs, even though the seed was the same. This confirmed that the source of randomness was not in the Python-level seeding but deeper, in the GPU computation itself.

⚠️ What Is Fixed and What Is Not

Source of Randomness Status Why
Train / val split ✅ Fixed Uses np.random.RandomState(seed)
Initial weights, dropout, batch order ✅ Fixed Depend on torch.manual_seed(args.seed)
Augmentation (flip, brightness, translation) ⚠️ Fixed but fragile Uses Python's random, which the script does not seed. It is saved because PyTorch reseeds random in each DataLoader worker. With num_workers=0 it would stop being reproducible.
GPU convolutions (cuDNN) ❌ Not fixed Some algorithms, especially in gradient computation, sum in an order that varies between runs.

🧩 How a Minimal Difference Ends in a Different Model

1. Rounding

In floating point, adding the same numbers in different order gives results that differ in the last decimal, on the order of 1e-7. cuDNN does not fix that order because not fixing it is faster.

2. Accumulation

That barely different gradient changes the weights slightly, which changes the next gradient. After thousands of batches, the two runs are already on different paths.

3. Thresholds

The script makes yes/no decisions based on val_mse: saving model_best.pth, lowering the LR (ReduceLROnPlateau), and early stopping, all with min_delta = 1e-4. If one run improves by 0.00011 and another by 0.00009, one resets the patience counter and the other does not. From there they diverge completely: different LR, different number of epochs, different saved model.

📌 Proposed Solution — Three Levels of Determinism

The following is a proposed solution to be applied to the training script. It is structured in three levels of increasing strictness.

✅ Level 1 — Seed Everything and Request Deterministic cuDNN Algorithms

In main(), replace the line torch.manual_seed(args.seed) with:

random.seed(args.seed)
np.random.seed(args.seed)
torch.manual_seed(args.seed)
torch.backends.cudnn.deterministic = True
torch.backends.cudnn.benchmark = False

For this model, this is usually enough. Training may become somewhat slower.

✅ Level 2 — Strict Mode, If Level 1 Is Not Enough

At the beginning of the file, before importing torch:

os.environ.setdefault("CUBLAS_WORKSPACE_CONFIG", ":4096:8")

And in main(), after the Level 1 lines:

torch.use_deterministic_algorithms(True)

In this mode PyTorch raises an error if any operation does not have a deterministic version, and the message says which one. If you prefer a warning instead of an error, use torch.use_deterministic_algorithms(True, warn_only=True).

✅ Level 3 — Shield the DataLoader

Make augmentation not depend on the internal detail of the workers. In train_one_dataset, before creating the loaders:

def seed_worker(worker_id):
    s = torch.initial_seed() % 2**32
    random.seed(s)
    np.random.seed(s)

g = torch.Generator()
g.manual_seed(seed)

And add to train_loader these two arguments:

worker_init_fn=seed_worker, generator=g,

🧪 How to Verify It Worked

Run the same command twice with a few epochs and compare the per-epoch lines:

python entrenar_definitivo.py --csv datasets/<dataset>/data.csv --epochs 3 --seed 42 > a.txt
python entrenar_definitivo.py --csv datasets/<dataset>/data.csv --epochs 3 --seed 42 > b.txt
diff <(cut -d'(' -f1 a.txt) <(cut -d'(' -f1 b.txt) && echo "IDÉNTICAS"

If it prints IDÉNTICAS, train_mse and val_mse match to the sixth decimal and training is repeatable. If there are differences, move to Level 2.

📌 Limits of This Solution

  • Only in the same environment. Repeatability holds for the same GPU, the same PyTorch, CUDA, and cuDNN versions. If the environment is reinstalled, the same seed may give a different result.
  • Does not recover a previous run. Training done weeks ago was without determinism, so no seed reproduces it exactly. These changes guarantee that runs from now on can be repeated.
  • Repeatable does not mean better. Fixing randomness gives you always the same sample of noise. To know if a configuration is good, train it with several seeds (--seed 1, 2, 3) and compare.

🚀 Part 2 — Behavior Metrics with CARLA in Docker: First Successful Run

✅ Behavior Metrics Is Now Running on Ubuntu 26.04 with an RTX 5070

Behavior Metrics now drives a Tesla in CARLA 0.9.15 and saves metrics. Two items remain pending: displaying the image in the frame_0 panel and connecting the PilotNet model.

🔧 How It Works

Behavior Metrics is a JdeRobot tool that puts a "brain" to drive in a simulator and measures how well it does, to compare brains under the same conditions.

Piece What It Does In This Installation
Simulator Provides the world, car, and sensors CARLA 0.9.15 in Docker container carla-bm, port 2000
Config YAML Defines car, sensors, brain, map, and where to save results configs/CARLA/default_carla_api.yml
Driver Reads the YAML, creates the world, and connects everything; -g opens the interface driver_carla.py
Brain Python script that receives sensors and returns throttle, steering, and brake brain_carla_slow_and_turn_api.py (simple rules, no neural network)
Metrics Step-by-step log (CSV) and summary (JSON) of each recording Folder with date and time inside behavior_metrics/

✅ Installation Steps Followed

These are the commands that left the environment working; pip check finished without conflicts. They only need to be repeated if reinstalling.

1. Clone the repository (noetic-devel branch, the main one):
cd ~ && git clone https://github.com/JdeRobot/BehaviorMetrics
2. Environment and base dependencies. PyTorch, TensorFlow, and TensorBoard are excluded because the file versions are incompatible with each other and with the GPU:

📌 Patch to Use CARLA in Docker

Without this change, Behavior Metrics closes your simulator on startup. The launch_env function in utils/environment.py does three things:

  1. Calls close_ros_and_simulators(), which runs killall -9 on CarlaUE4.sh and CarlaUE4-Linux-Shipping. The container process is visible from the system, so it kills it.
  2. Requires the CARLA_ROOT variable, even though it only uses it if it has to launch CARLA on its own.
  3. Checks if a CARLA is already running and, if so, does not launch another.

The patch adds an escape hatch controlled by the environment variable BM_EXTERNAL_CARLA=1. It was applied once and left a copy of the original in utils/environment.py.bak:

cd ~/BehaviorMetrics/behavior_metrics
sed -i.bak '/^def close_ros_and_simulators/a\    if os.environ.get("BM_EXTERNAL_CARLA") == "1":\n        return' environment.py

With CARLA_ROOT=/tmp, point 2 is satisfied, and point 3 already plays in our favor: the output shows Carla running: True.

Limitation: with closing disabled, Behavior Metrics does not clean the world when finished. Restart the container between sessions to start clean.

✅ Session Startup

Two terminals are needed: first the simulator, then Behavior Metrics.

Terminal 1: simulator. Stop your CARLA 0.9.14 containers first, because they use conflicting ports. Wait until the CARLA window shows the map.
sudo docker rm -f carla-server carla_montado carla-bm 2>/dev/null
sudo docker run -d --name carla-bm --privileged --gpus all \
  --net=host \
  --env="DISPLAY" \
  --env="NVIDIA_VISIBLE_DEVICES=all" \
  --env="NVIDIA_DRIVER_CAPABILITIES=all" \
  --volume="/tmp/.X11-unix:/tmp/.X11-unix:rw" \
  carlasim/carla:0.9.15 ./CarlaUE4.sh -quality-level=Epic -nosound -world-port=2000
Terminal 2: Behavior Metrics. Use a new terminal, without venv_py37 active.
cd ~/BehaviorMetrics/behavior_metrics && source ../venv/bin/activate
export ROS_VERSION=None BM_EXTERNAL_CARLA=1 CARLA_ROOT=/tmp
export OBJECT_PATH=$PWD/configs/CARLA/CARLA_launch_files/CARLA_object_files/parked_car_objects.json
python3 driver_carla.py -c configs/CARLA/default_carla_api.yml -g

Two windows open: pygame window, with the Tesla seen from behind in Town01, and driver_carla.py, the Behavior Metrics interface.

📌 Two Cautions When Reading These Metrics

  • Collisions are counted per event, not per crash. Staying stuck against the fence adds one at every instant, which is why the "per km" figures come out enormous (547,200 collisions per km).
  • Deviation and percentage completed are measured against PerfectLap, the reference route from the config. You must check that it corresponds to the route you want to evaluate.
